# Modern AirDrop on Mavericks

AquaTransport adapts Mavericks' original `sharingd` to modern AirDrop. Finder keeps its native discovery, acceptance, progress, file extraction, destination placement, conflicts and errors. The adapter changes transport and protocol metadata; it does not parse transfer archives. No SIMBL or Python runtime is required. TLS uses AquaTransport's existing OpenSSL engine and the native Keychain identity.

## Compatibility

Activation requires all of the following:

- Darwin 13, x86_64 `/usr/libexec/sharingd`, UUID `C4FA4877-6F18-3715-A5C8-DEDF9026BDF9` (the validated 10.9.5 binary).
- `/dev/tap0` present as a character device.
- Exactly one usable `IO80211Interface` with a BSD interface name; no vendor, PCI ID or driver-model whitelist.
- Exactly one Bluetooth controller with LE support. Bluetooth may be powered off when the adapter loads.
- Root-owned module, helper, launchd job, radio executables and safe ancestor directories.
- No `disable-modern-airdrop` entry in AquaTransport's `config/flags.txt`.

Required native symbols, methods, encodings and ownership are checked before hooks are installed. Unsupported systems retain their original AirDrop behavior. The universal loader has no new Foundation or IOKit linkage; the independent Objective-C module targets 10.9 only. It loads before SharingDaemon starts, outside the universal loader's constructor. Wi-Fi models are intentionally open to tester feedback. Multiple Wi-Fi interfaces remain ineligible because this adapter cannot safely choose which radio to take over.

On each Mavericks boot, AquaTransport's package-level bootstrap loads the socket-activated radio-helper job on 64-bit Darwin 13 when `disable-modern-airdrop` is absent, the helper's job file is root-owned, the TAP driver bundle (`tap.kext` in `/Library/Extensions` or `/System/Library/Extensions`) is installed, and IOKit shows exactly one named `IO80211Interface` and one Bluetooth controller with LE support. These are durable facts about the installation and hardware, so the job is not registered on a Mac that can never use it. The bootstrap runs when its launchd job loads and again on Mavericks' `com.apple.iokit.matching` events for `IO80211Interface` and `IOBluetoothHCIController`; launchd delivers services that already exist when the job loads as well as ones that register later. Runtime state is not part of this decision. The tap kext's own LaunchDaemon creates `/dev/tap0` several seconds after the bootstrap runs, and the Wi-Fi channel list depends on the country code that Wi-Fi sets at runtime, so neither has a reliable boot-time answer. sharingd's adapter checks the TAP device node and hardware before installing, and the helper's start command checks the TAP device node, the Wi-Fi interface, channel 149, Bluetooth LE and Bluetooth power on every request; sharingd retries pending browser and receiver starts, so a radio that becomes ready later is picked up without a reboot. A Wi-Fi card without channel 149 support therefore keeps an idle, never-connected helper job. There is no readiness retry timer, polling loop, path watch or startup deadline. The bootstrap consumes queued XPC events and exits after one second without another event; this is an idle-exit timer, not a hardware retry. Each skipped registration logs the missing prerequisite. Before loading either optional feature job, the bootstrap queries launchd and skips already registered jobs, including idle socket jobs; a failed query also prevents loading. Registered AirDrop jobs are skipped before any hardware query, leaving live radio access to the helper. This avoids Mavericks replacing a live socket during a rejected duplicate load. Failed queries and loads are logged; another matching event, the package postinstall or the next boot runs the bootstrap again. Anisette is checked once per bootstrap invocation. The bootstrap is intentionally independent of the AirDrop payload so other optional features can use it later. The payload remains installed when ineligible. Reboot after changing the disable flag so the daemon adapter and helper use the same setting. LE capability is checked independently of the controller's current transport connection state. The helper independently checks hardware, Bluetooth power, TAP and the current console user before taking the Wi-Fi radio. Its commands cannot specify executable paths or arbitrary arguments. Missing dependencies or startup failure unwind radio ownership gracefully. OWL then requires monitor-mode activation and radiotap capture; failure stops the radio processes and restores the Wi-Fi lease. Passing these capability checks does not establish successful AWDL communication on an untested card.

Finder and ShareKit's separate AirDrop plug-in show a Bluetooth prompt when Wi-Fi is on and Bluetooth is off. Its button powers on Bluetooth; sharingd retries pending AirDrop browser and receiver starts after the controller powers on. The native Wi-Fi warning remains available when Wi-Fi is off. AirDrop never powers Wi-Fi on: while Wi-Fi is off, sharingd neither asks the helper to start nor retries pending starts, and logs that it is waiting for Wi-Fi; the helper's start command also refuses with Wi-Fi off. Once Wi-Fi is turned on, including from Finder's native **Turn On Wi-Fi** button, sharingd's own Wi-Fi power notification retries the pending starts immediately, with the five-second pending retry as a fallback. Finder decides between its AirDrop view and the Wi-Fi prompt from `_CSIsWirelessP2PEnabled()` and re-evaluates only when the `WirelessEnabled` value published by sharingd's AirDrop server to Finder's listener changes. A server whose start waits for Wi-Fi therefore publishes its current `WirelessEnabled` value (`publishedInfoChanged:`) when the start is deferred, as a started server would; otherwise the later power-on is not a change for Finder and the prompt stays until the user leaves and reopens AirDrop. Live tests with Finder's layout decision instrumented showed no re-evaluation after power-on without this publication, and a re-evaluation within one second, with the AirDrop view shown, in three consecutive runs with it. Turning Wi-Fi off during a session makes the helper stop OWL and Bluetooth advertising within a second and leaves Wi-Fi off; sharingd's heartbeat then reports the lost lease and waits for Wi-Fi before restarting. Finder also provides **Search for an Older Mac**. Selecting it stops modern browser and receiver sessions, restores ordinary Wi-Fi and restarts them using Mavericks' native AirDrop protocol. Active modern and native transfers delay a protocol switch until they finish. Leaving the Finder AirDrop view restores modern mode; a session heartbeat also restores modern mode if Finder exits unexpectedly. The choice is not stored on disk. The Finder and FinderKit UI hooks are limited to the validated Mavericks binary UUIDs.

The Bluetooth prompt uses Finder's actual `TAirDropNotAvailableViewController` and localized `AirDropNotAvailableView` nib. Its artwork, heading, fields, button and layout are native; the adapter substitutes Bluetooth for the Wi-Fi name and changes that instance's button action. ShareKit uses the corresponding native FinderKit Wi-Fi strings in its existing controls. When both radios are off, the original Wi-Fi prompt takes priority. No custom Bluetooth panel is drawn. Live comparison with Wi-Fi off verified the same artwork, field placement and button styling, and a click on the native Bluetooth button powered the controller on.

Finder's footer keeps the first sentence from its existing localized description, including the native text styling, using locale-aware sentence boundaries. **Don't see who you're looking for?** opens a native transient popover with the supplied explanatory copy and **Search for an Older Mac** button. The popover asks iOS users to set AirDrop to Everyone, using normal text. It closes when leaving AirDrop. The new UI strings use `AirDropUI.bundle` and follow Finder's localization, with English fallback. Spanish, French, German, Brazilian Portuguese (Mavericks' `pt`), Japanese, Korean and Simplified Chinese are included. The introductory sentence continues to come directly from Finder. Translations and button widths are covered by the UI regression; the editable copy is listed in [AIRDROP-TRANSLATIONS.md](AIRDROP-TRANSLATIONS.md).

## Wi-Fi and transfer lifetime

Opening native AirDrop acquires the radio, disconnects ordinary Wi-Fi and starts OWL and Bluetooth advertising. Browser, receiver and transfer operations own independent leases. Navigating away cannot release the radio while a send or receive still owns it. Incoming transfers retain their native receiver until completion, cancellation or failure; deferred receiver shutdown uses the original stop method. Reopening cancels pending shutdown.

Mavericks starts a new receiver only after the stopped receiver's HTTP server reports that its last connection has closed; until then, `startHTTPServer` returns without logging, the stopped receiver's Bonjour record stays published, and its listener abandons every new connection. A modern peer that leaves mid-exchange can hold a connection open indefinitely, which would leave receiving unavailable until sharingd exits. Five seconds after a receiver stops, and while no receive is running, the adapter invalidates connections the stopped server still holds and logs how many. Native close handling then withdraws the old record and starts the waiting receiver. Checks repeat every five seconds, up to twelve times, and end when the table empties or the server restarts.

After the final owner releases its lease, a three-second grace period accommodates native object handoffs. The helper restores the previous Wi-Fi association when appropriate without retrieving passwords, unless Wi-Fi was turned off during the session. A 15-second heartbeat renews the helper's 45-second lease; console-user changes and radio-process exits also trigger cleanup. Failed heartbeats reacquire ownership while native owners remain alive.

## Protocol and reliability

Modern `/Discover` metadata populates native Bonjour peers. Scoped IPv6 connections are limited to known AirDrop endpoints on TAP. The native sender creates the metadata and archive; the adapter adds modern offer fields and the matching upload header.

Adapted outgoing offers omit Mavericks' legacy `SenderEmailHash`, and Bonjour announcements omit `ehash`. Incoming AirDrop discovery metadata also excludes that unverified identity claim; unrelated service discovery is unchanged. This adapter advertises Everyone-mode discovery without a verified Apple ID identity. Keeping that hash made another Mavericks receiver resolve the sender's Apple ID and demand client-certificate proof; the captured Mac-to-Mac requests had no client trust object and returned HTTP 401 before showing an acceptance prompt. Mavericks first looks for an existing discovery node when handling an offer, so leaving `ehash` in Bonjour would reproduce the rejection even with a fresh cache and an anonymous offer. Omitting the identity claim from both paths preserves ordinary native acceptance without marking the sender as a verified contact or same-account device. The offer regression covers binary/XML metadata, native file fields, repeated adaptation and transfer-ID stability.

An accepted `/Ask` keeps its HTTP connection for `/Upload`, preserving Mavericks' native acceptance state. At receive completion, the adapter closes the consumed native input stream after BOM extraction returns, within the native adaptive receive call. This releases a producer join that otherwise waits for more body data. Native extraction status, placement and final response remain responsible for success or failure.

EOF delivery is idempotent per native connection/stream open. This addresses concurrent offer parsing seen in a native crash; duplicate EOF as that crash's exact cause remains an inference. Offline tests exercise the guard without reproducing the native crash.

OWL adopts master schedule changes immediately, retains clock mapping across bounded capture delays and checks the actual multicast transmit channel. Normal RSSI admission filtering prevents weak timing peers from taking over. Each radio session gets a new service-update identifier. Active native publishers reconfirm their own service-list PTR after three seconds, every five seconds during the first minute and every thirty seconds thereafter. This recovered a captured missing-recipient case without restarting the receiver or radio. Publication checks stop with their owner.

## Build, install and remove

Run `./build-macos.sh` for the complete payload. It calls `tools/build-airdrop.sh`, which can also rebuild the independent AirDrop payload alone. OWL and pinned libev sources remain vendored in the development tree; only runtime files enter the installation stage. No development checkout or `/usr/local` runtime dependency is required.

`sudo ./install-macos.sh install` installs the complete staged build, including the socket helper. The Packages project also includes the AirDrop payload and uses its existing postinstall for helper setup during installation and updates. The single shipped `Uninstall.command` directly unloads/removes the helper, restores Security.framework and removes AquaTransport. No install or uninstall script is installed in `/usr/share`. Installation or updates can end an active transfer; perform them while AirDrop is idle.

Setting `disable-modern-airdrop` and rebooting disables activation and leaves the radio-helper job unloaded while retaining the files. Remove the flag and reboot to make an otherwise eligible installation available again.

The development Mac now runs through AquaTransport alone. The former ModernAirDrop SIMBL bundle and helper were moved out of their load locations; rollback copies and diagnostic evidence are retained separately.

## Validation and limits

On October 6, 2026, AirDrop again repeatedly reported “radio unavailable” with no helper socket while TAP, Bluetooth LE and Wi-Fi channel 149 were all available. The boot log showed the bootstrap running at 15:46:20, registering Anisette but not the radio helper, and the tap kext creating `/dev/tap0` at 15:46:24, with `en1` attaching in airportd at 15:46:25. Logs from the four boots between October 4 and October 5 show the same order every time: the tap kext loaded four to eight seconds after the bootstrap, and no boot registered the helper. In the same boots, the Bluetooth controller's `registerService` and Wi-Fi's data-link attach were logged within a second of the bootstrap. Running the bootstrap after boot registered the helper, and the running sharingd immediately started OWL, Bluetooth advertising and TAP; a Bonjour browse found the AirDrop service on TAP and the user confirmed AirDrop worked. The bootstrap regression covers unsupported or disabled systems, an untrusted job file, a missing TAP driver, missing radios, a radio arriving by event after startup, registration without the TAP device node, repeated events against an already registered job, query failures, interrupted waits, failed loads followed by successful registration and idle exit. It also checks that the bootstrap job has exactly the two IOKit matching events and no timers or path watches. Whether `BSD Name` and `HCISupportedFeatures` are always populated by the time their matching events are delivered has not yet been observed across a fresh boot.

On September 30, 2026, AirDrop repeatedly reported “radio unavailable” with no helper socket, even though TAP, Bluetooth LE and Wi-Fi channel 149 were available. The failed boot prerequisite was not logged. Registering the missing helper let the existing sharingd automatically start OWL, Bluetooth advertising and TAP. A live Bonjour browse found the AirDrop service on TAP. Follow-up testing confirmed an incoming native extraction and completed transfer at 09:50:47, an outgoing transfer with HTTP 200 completion at 09:51:32, and user-confirmed receipt on the Mac. Before those successes, captures showed continued iPhone AWDL announcements but unanswered TCP connection attempts, with no logged injection errors or kernel capture drops. The captured iPhone announcements averaged approximately -73 dBm on the 5 GHz channels; the cause of the failed data exchanges remains unproven. Radio restarts, a Wi-Fi power cycle and sharingd restarts were performed during investigation, so recovery cannot be attributed conclusively to one intervention. Local diagnostic evidence is retained under `build/airdrop/diagnostics-2026-09-30/`.

Later that day, discovery again failed intermittently with `/Discover` timeouts while TAP was up and the radio process stayed alive. An outgoing HTTP 401 at 11:36 was a user-declined offer, not an unexpected authentication failure. The iPhone appeared at 11:47 without a radio or sharingd restart; transfers succeeded in both directions at 11:48–11:49. The Mac-to-iPhone upload took about 29 seconds for less than 1 MB. A passive radio capture before recovery accepted 217 iPhone AWDL action frames and showed a four-active-slot channel sequence. This confirms that the Mac heard iPhone announcements but does not establish that transmitted data reached the iPhone. A later 20-packet ping to the previous link-local address got no replies, but a simultaneous Bonjour browse found no iPhone advertisement and its ten-minute Everyone window may have expired; this probe is inconclusive. The root-owned `radio-diagnostics` marker was then enabled and OWL restarted once at 12:06; TAP recovered and OWL now emits per-second send, injection, channel, and capture-drop counters to syslog. With the iPhone unlocked and advertising again at 12:13–12:16, Bonjour listed its service and resolved the same IPv6 address used for probing, yet neither device showed the other in AirDrop. A paired TAP/radio capture recorded 15 requests leaving TAP for the iPhone's AWDL MAC with no response. OWL counted transmissions with zero injection failures, wrong-channel sends, or capture drops. The monitor capture does not include this Mac's own transmitted frames, so over-the-air delivery is still unverified. The intermittent radio data-path cause remains unresolved.

The user confirmed active monitor mode is available and the iPhone was already close to the Mac. A temporary fixed-channel-6 OWL run heard strong iPhone announcements but did not produce replies; its Bonjour service was absent during that measurement, so the channel comparison was inconclusive. The original channel-following helper was restored byte-for-byte. OWL diagnostics now also count failed action and multicast injections and reject short `pcap_inject` writes. After the radio restarted at 12:47, Bonjour again showed the iPhone and 12 of 12 link probes returned, with a 2–468 ms round-trip range. All recorded injection-failure counters were zero. This recovery followed a restart, but the counters do not identify the failed state or prove the restart caused recovery. Finder then showed three iPhone entries while Bonjour had only one or two iPhone service identities. The browser removal path now clears and republishes Finder's cached peers when a modern Bonjour identity disappears; its regression passes, and the new adapter was installed and loaded by restarted sharingd and Finder at 12:55. The user subsequently confirmed the extra iPhone entries were gone.

At 13:07, an iPhone Bonjour service was visible but 12 of 12 link probes failed; the OWL injection-failure and capture-drop counters remained zero. By 13:17, 11 of 12 probes succeeded without another restart. At 13:20, the peer and its TAP neighbor entry disappeared. The user then reported that the iPhone's Everyone for 10 Minutes window had expired and re-enabled it. The peer and neighbor returned, both devices became visible, and 20 of 20 probes succeeded. A one-minute probe during the renewed window received 115 of 120 packets, with two duplicate responses and 2.7–599 ms latency. The user completed transfers in both directions at 13:23–13:24; the outgoing offer returned HTTP 200, and the Mac-to-iPhone transfer still felt somewhat slow. Selecting Search for an Older Mac then removed the iPhone from Finder, verifying the original stale-peer fix in a live session. These observations establish that the expired visibility window explained at least the 13:20 peer loss. They do not explain the 12:13–12:16 failure while the iPhone was advertising, or prove that the radio data path is reliable.

With Finder AirDrop subsequently closed, the OWL radio helper exited, `tap0` disappeared, and `en1` no longer had its monitor capture flag by 13:42. Reopening Finder started a new helper and `tap0`, and the user confirmed both devices were visible again. This verifies the close-and-reopen radio lifecycle in the live session. The helper had briefly remained active after the native-to-modern mode switch at 13:30, so an immediate process check after closing Finder would have been misleading.

On September 28, 2026, live tests verified Bluetooth power-on from Finder and the Share sheet, switching Finder to the older protocol, and restoring modern discovery after leaving and reopening AirDrop. ShareKit reuses its native message and buttons and requests radio status/power-on from Finder because its sandbox blocks direct radio control. Finder controls sit above its cached AirDrop artwork. Installation now unloads the old helper job before reloading its socket, and delayed receiver cleanup uses a weak lifetime state to avoid accessing a receiver destroyed during shutdown. UI regression coverage includes the case where Bluetooth changes between displaying and clicking its button: that click cannot become Send. New end-to-end file transfers were not part of these UI checks.

On September 21, 2026, Mac-to-Mac offers returned HTTP 401 when Mavericks resolved a legacy Apple ID hash but had no client trust object. Removing the offer hash alone left the named Bonjour discovery path affected. After also removing discovery identity claims, desktop receive logs showed successful native extraction and the user confirmed the formerly failing laptop-to-desktop transfer completed. Desktop-to-laptop transfer had already been confirmed. Publication, discovery-cache, offer-metadata and stream-event regressions passed.

On September 25, 2026, an iPhone-to-Mac transfer failed with CFHTTPServer error 1104, after which the iPhone could no longer find the Mac. A `/Discover` connection from the iPhone remained open on the stopped receiver with an incomplete response. The replacement receiver never started, while the iPhone's TLS connections to the stale advertised port were abandoned without a ServerHello. Invalidating that one connection in the running sharingd started the replacement receiver immediately, and the iPhone found the Mac again. The server-drain regression covers this lifecycle.

On the development Mac, the user confirmed native transfers in both directions with an iPhone 13 mini running iOS 26.6.2, repeated discovery after closing/reopening AirDrop, and successful operation after the transfer-lifetime fix. The last live transfer retained its radio lease from 19:52:01 until 19:54:33 on September 14, 2026. Temporary packet capture and buffer monitoring were stopped after validation.

Offline regression scripts under `tools/test-airdrop-*.sh` cover clock delay, master scheduling, multicast scheduling, peer filtering, service-session identity, publication/EOF lifetimes, native receive stream completion, transfer ownership, protocol switching, Finder-session expiry and stopped-receiver connection drain. The receive fixture exercises real CFHTTPServer/BOM through AquaTransport TLS with an open-ended body; its producer models the native adaptive lifetime, not the native codec. Transfer tests cover navigation, parallel operations, completion, cancellation, errors, abandoned operations, receiver reopening and helper failure.

Hardware eligibility is capability-based; this is not a validated compatibility claim for every legacy Mac. Additional hardware and actual 10.6/10.7/10.8 hosts have not been tested during this migration. The full TLS selftest requires an unpatched Security.framework and was not run on this already-patched host. Transfer throughput remains limited by this radio implementation; occasional offer latency is not fully explained. Longer use may expose additional lifecycle issues.
