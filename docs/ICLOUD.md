# Experimental iCloud authentication for OS X

The `aquatransport_gsa.dylib` module translates legacy iCloud password sign-in
into GrandSlam authentication on **OS X 10.7–10.9**. AquaTransport's TLS engine
still supports 10.6; this module does not add iCloud to Snow Leopard.
The authentication adapter is enabled by default.

**Status: GrandSlam sign-in and trusted-device 2FA reached successful account
creation on 10.9.5 with a real account. After adding saved-token device headers,
the native helper's account refresh returned HTTP 200. Read-only Calendar and Contacts
discovery returned HTTP 401 with the saved modern token alone and HTTP 207 with
device headers. The user confirmed both Calendar and Contacts work with the native DAV adapter.
Mail failed with the account-helper fixes alone; the user confirmed it works after
installing the six-field ATOKEN adapter on 2026-09-09. All 63 offline checks passed
for that build, including native MailCore tests with synthetic credentials.**
The mock tests pass through the installed AOSKit framework's actual
`AOSRequest` / `CFURLConnection` path. They cannot establish that Apple's current
servers accept this client identity, issue the required tokens, or return an account
settings dictionary that the iCloud preference pane accepts. Offline tests do not
change existing accounts.

## Build

The module needs a compiler that supports Objective-C garbage collection. Mavericks
System Preferences supports GC; loading an incompatible library into a GC process
fails. The ordinary TLS engine and loader continue to use the default compiler.
Apple clang 6.0 on this machine has removed GC; upstream LLVM **3.4.2** works.
`AQUATRANSPORT_GSA_CC` can select a suitable compiler already installed.

To obtain the official compiler used for this port (one-time, about 80 MB):

```sh
curl -fL 'https://releases.llvm.org/3.4.2/clang+llvm-3.4.2-x86_64-apple-darwin10.9.xz' -o /tmp/aquatransport-clang.tar.xz
shasum -a 256 /tmp/aquatransport-clang.tar.xz
# Expected: eec3e0739aa86e8e2f59b104eae36c3d710b7b7b9a68ba202cda1320fa9dd0f5
mkdir -p build/gsa-toolchain
tar -xf /tmp/aquatransport-clang.tar.xz -C build/gsa-toolchain --strip-components=1
./build-macos.sh
./tools/gsa-selftest.sh
```

The archive is linked from the [official LLVM releases page](https://releases.llvm.org/download.html#3.4.2).
It is a development tool and is not included in the installer. After toolchain setup,
builds and the GSA tests require no network. This particular compiler binary runs on
Mavericks; building on earlier systems requires a compatible GC-capable compiler.

The build produces loader, TLS engine and GSA dylibs under
`build/stage/usr/share/aquatransport/`. All have i386 and x86_64 slices and zero
exported symbols. The build checks GC compatibility for the GSA x86_64 slice;
32-bit processes use retain/release. The package project and command-line installer
include the new module. Existing `.pkg`/DMG binaries are not regenerated by the build.

## Anisette prerequisite

GrandSlam needs fresh device authentication data as well as SRP. With no server
configured, the adapter tries `+[AOSUtilities retrieveOTPHeadersForDSID:@"-2"]` from
the system's AOSKit. It returned **no headers on this machine**, both inside and
outside the development sandbox. Its existence does not establish that the Mac has
usable device provisioning. The adapter does not attempt to provision or modify it.
If local generation returns nothing, the adapter uses the provider protocol from
GSAPort at `https://icloud.podpod123.com/anisette.php`, including its required signed
request headers. That fallback sends the Mac's hardware UUID and exposes its public
IP to the provider; it does not send Apple account credentials.

To override both automatic providers, put a server URL, and nothing else, in
`/usr/share/aquatransport/config/gsa-anisette-url.txt`. It must answer an unauthenticated
GET with a JSON dictionary containing these string values:

```json
{
  "X-Apple-I-MD": "fresh one-time device value",
  "X-Apple-I-MD-M": "machine value",
  "X-Apple-I-MD-LU": "local user identity",
  "X-Apple-I-MD-RINFO": "routing information",
  "X-Mme-Device-Id": "device identity"
}
```

The device identity must remain consistent across requests. The adapter adds the
current time, timezone and locale. It accepts the optional `X-Apple-I-SRL-NO` string,
and the optional `X-MMe-Client-Info` string, retaining the provider's client identity
in both the HTTP headers and GrandSlam client data. Other fields are ignored.
HTTPS is required except for HTTP on loopback. Redirects
are rejected. A server requiring a V3 provisioning handshake needs a separate adapter
that exposes this GET interface; a V3 URL alone is not sufficient.

The built-in GSAPort provider uses `X-Device-Uuid`, `pk` and `podkey` request headers;
a custom server URL instead uses the plain GET interface above. Passwords, Apple IDs,
verification codes, Apple tokens and cookies are never included in either provider
request. The server still sees the connecting IP and supplies device identity
material. [SideStore documents why shared older anisette identities can cause
account locks](https://docs.sidestore.io/docs/advanced/anisette).

## Install and try a sign-in

Install or update the built libraries with:

```sh
sudo ./install-macos.sh install
```

GrandSlam authentication is enabled automatically; no enable flag is needed. An
update preserves the existing Security.framework patch, its original backup, and
configuration files. A source build alone does not update installed libraries.

Quit and reopen System Preferences, then sign in normally. A reboot is not required
for the preference pane's own requests. If an account helper owns the request, that
process must also be restarted to load updated code.

For trusted-device two-factor authentication, the first attempt requests a code and
returns an authentication failure to the old client. Approve the request on the
trusted device, then retry within five minutes using **your password immediately
followed by the six-digit code**. A code by itself is not supported. Keep the same
preference pane/helper process running between attempts. Pending state stores only
the verification session, not the password, and is bounded to 32 accounts per process.
Expired entries are removed on the next attempt.

The old pane may show a generic authentication failure rather than instructions for
entering the code. The user completed this two-attempt flow with a real account. SMS-only
verification (`secondaryAuth`), account recovery, account creation, terms acceptance,
Game Center and Find My are not implemented. The experimental iMessage profile
adapter is described below; native iMessage sign-in is user-confirmed on Mavericks. This module does not
guarantee that iCloud services work after account creation.

To turn the capability off, add `disable-icloud-gsa` to
`/usr/share/aquatransport/config/flags.txt`. Remove that line to turn it back on. An already running
exchange finishes unless its caller cancels it. Restart the process to unload the
module and discard pending verification state. Anisette or protocol errors stop the
attempt; the adapter does not silently retry using the submitted password.

## Integration and authentication details

The protocol flow was studied in [Epixx512/GSAPort's Tweak.x](https://github.com/Epixx512/GSAPort/blob/main/Tweak.x).
This is an independent implementation of the relevant exchange, not a vendored copy
of that unlicensed repository. Local anisette discovery was cross-checked against
[AltServer's AOSKit integration](https://github.com/altstoreio/AltStore/blob/marketplace/AltServer/Anisette%20Data/AnisetteDataManager.swift).

The C rewriter loads the separate Foundation module from beside the engine only
when GSA is enabled and a request addresses the Apple authentication or DAV hosts, or
Mail sets up TLS to an iCloud IMAP/SMTP host with legacy MailCore already loaded. It
requires Foundation already present and Darwin 11 or later. There is no Foundation
load from the Security constructor. In particular, installing AquaTransport does not
load it into sshd, loginwindow, or non-networking processes at launch.

The module intercepts HTTPS requests on `setup.icloud.com`, port 443, for:

* `/setup/login_or_create_account`
* `/setup/iosbuddy/loginDelegates`
* `/setup/authenticate/<Apple ID>` (including the literal `$APPLE_ID$` placeholder)
* `/setup/get_account_settings` with a numeric DSID and a modern `E`-prefixed MME token

It recognizes preemptive Basic authentication or a plist body containing
`username`/`apple-id` and `password`. It lowercases the account identifier before
the GrandSlam handshake and token exchange; password spelling is preserved.
Existing-account settings requests instead retain their DSID/token, method and
body and receive fresh anisette headers. They never enter the password or 2FA
flow. Older tokens and password-based settings requests retain native behavior.
Requests with streamed bodies, unsupported
credential formats, or different endpoints retain their native behavior. There is
no generic browser-login or `NSURLSession` support claim. With GSA enabled, general
redirect/header rules are bypassed for `gsa.apple.com` and `setup.icloud.com` so
they cannot redirect credentials or overwrite authentication headers.

Calendar and Contacts use a separate streaming `NSURLProtocol` for HTTPS
on `caldav.icloud.com`, `contacts.icloud.com`, and their `p<digits>-` shard hosts.
Native discovery URLs can include an escaped username. Calendar port 8443 and
Contacts port 8843 are mapped to port 443; resource paths and usernames are
preserved. URLs containing passwords and other ports retain native behavior.
It adds device authentication data, cached for 60 seconds per process. The native
client still selects credentials and handles authentication challenges; request
methods, bodies, and DAV response headers are preserved. Response data streams
without the authentication transport's 4 MB cap. Redirects return to the native
client after device headers are removed; cross-origin redirects also lose any
explicit Authorization header. A redirected DAV request must pass the host check
again. General redirect/header rules cannot modify these reserved service hosts.
The same `disable-icloud-gsa` flag disables the sign-in, DAV and Mail adapters.

### iMessage profile authentication

Adapter 9 adds default-on handling for HTTPS POST requests to
`/WebObjects/VCProfileService.woa/wa/authenticateUser` on exactly
`profile.ess.apple.com` and the older `service.ess.apple.com`, port 443. Other
profile operations and the subsequent IDS certificate/registration exchange remain
native. General redirect/header rules bypass these two hosts while GSA is enabled.

Mavericks' `IDSProfileAuthenticationMessage` sends `username` and `password` in
a plist; its base class requests compression. This agrees with the gzip request
documented in [Quarkslab's protocol investigation](https://blog.quarkslab.com/imessage-privacy.html).
The adapter accepts uncompressed or gzip plists, limits both input and decoded
output to 1 MiB, and rejects malformed/compressed streams and unsupported encodings
without submitting the original password. Userinfo, nonstandard ports, query strings
and different paths are outside its scope.

It uses the existing GrandSlam handshake and trusted-device verification flow.
While verification is pending, it returns the native profile authentication error
5000 without contacting the legacy endpoint. Once GrandSlam issues a PET, adapter
10 exchanges it at `https://setup.icloud.com/setup/iosbuddy/loginDelegates`, requesting
only `com.apple.madrid`. It supplies the username/PET, device headers and
`X-Apple-ADSID`. Both the overall and delegate statuses must be numeric zero, and
`service-data` must contain nonempty `profile-id` and `auth-token` strings. Only then
are those server-issued credentials translated into the profile response expected
by Mavericks. Failed or malformed replies never become successful activation.
There is no fallback request to `authenticateUser`, and no token caching/replay.
The existing `disable-icloud-gsa` flag also disables this adapter.

The PET-to-delegate exchange is independently implemented with reference to
[rustpush's historical implementation](https://github.com/OpenBubbles/rustpush/blob/75e453ca691d3631275fe2a4621c6085b5a86567/src/auth.rs).
The legacy Madrid delegate follows the user's
[documented loginDelegates workaround](https://forums.macrumors.com/threads/tutorial-fix-facetime-game-center-login-grinning-squinting-face.2458114/).
The newer `com.apple.private.ids` delegate and its additional device-validation
exchange are not used here.

**Validation status:** On 2026-09-09, original numeric tracing showed HTTP 200 with
profile status 5000 for the password-only attempt, then HTTP 200 with 5068 for the
password-plus-code attempt. Mavericks maps 5068 to registration error 9 (generic
server error). Adapter 9 then successfully obtained a GSA PET in Apple's separate
`IMRemoteURLConnectionAgent` process, but the profile endpoint still returned 5068
when given that PET. Absence of the GSA module in `identityservicesd` itself does
not establish that interception failed: the HTTP request runs in the XPC agent.
Use ASL's `Seq` substring operator to find AquaTransport diagnostics; `C` alone is
case-folded equality, not a contains query.

Adapter 10 passes 98 offline checks, including compressed iMessage sign-in, 2FA,
failed delegates, missing credentials, malformed statuses, rejected redirects,
invalid server proofs, decompression limits, endpoint scope and the off flag,
alongside the existing iCloud/DAV/Mail checks. The user confirmed native iMessage sign-in succeeds with adapter 10 on 2026-09-09.
The offline 2FA tests run in one process; they do not verify preservation of pending
verification state across an XPC agent restart. FaceTime uses the same profile
endpoint, but its use of this delegate and repeated authentication are unverified.

### Mail ATOKEN device fields

The supplied Sequoia installer contains a materially newer `atoken.so` than the
earlier Yosemite/Sierra samples. Its mechanism is still named `ATOKEN`. Its
response contains six UTF-8 fields separated by five NUL bytes, without a trailing
NUL: authorization person ID, authentication person ID, token, then three device
fields obtained through SASL callbacks `0x4a05`, `0x4a06`, and `0x4a07`.
The order and separators were verified by executing the extracted plugin's pure
buffer-building routine with six synthetic strings; no account/network calls were
made. The extracted universal plugin's SHA-256 was
`a250098e6401b479a299f2131e172cd5b427038ccb9b2b5a95760ef25851cdc9`.

The corresponding Mail client fields are `machineID`, `oneTimePassword`, and
`clientInfo` in the newer
[MCSaslClient header](https://github.com/w0lfschild/macOS_headers/blob/master/macOS/PrivateFrameworks/MailCore/3445.104.11/MCSaslClient.h)
and [MFAccount interface](https://github.com/w0lfschild/macOS_headers/blob/master/macOS/PrivateFrameworks/Mail/3445.104.11/MFAccount.h).
The adapter maps these to the existing provider's `X-Apple-I-MD-M`, `X-Apple-I-MD`,
and `X-MMe-Client-Info` values, using its existing client identity if the optional
client-info field is absent. This mapping follows the client field order; the
Sequoia caller's client-info implementation was not recovered. The user confirmed
Mail works with this adapter after restarting Mail and testing the installed build.
Sending through SMTP has not been separately confirmed.

The C engine loads the adapter during `SSLSetPeerDomainName`, before taking a TLS
context lock, only for exact iCloud IMAP/SMTP hosts and with legacy MailCore already
present. The adapter replaces `_MCAppleTokenSaslClient initialResponse` in memory.
It preserves native credential retrieval and appends device fields only to an
existing three-field response with an `E`-prefixed token and an iCloud account
hostname. IMAP and SMTP hosts under `mail.me.com` and `mail.icloud.com`, including
their `p<digits>-` shards, are recognized. Other accounts and older tokens retain
native behavior. Device data is cached for 60 seconds per Mail process; credentials
are not cached by this adapter. Missing device data fails the local authentication
attempt. Neither Mail.app nor the system SASL plugins are replaced.

All Sequoia archives, extracted resources, analysis files and archive-reader tools
were confined to a hidden, mode-0700 `.noindex` temporary directory with a
`.metadata_never_index` marker. No image was mounted and no application bundle was
extracted or registered with LaunchServices. These temporary files were removed
after inspection; the supplied ISO was retained.

Local inspection of the supplied Yosemite and Sierra 10.12.6 installers found
only the legacy `ATOKEN` mechanism in their token plugins (versions 187 and 192).
Both construct `authorization-ID NUL authentication-ID NUL token`, without
additional device fields. Sierra's MailCore (3273) selects `ATOKEN`; Mail obtains
its token through the system account's `icaAuthToken` accessor. No `ATOKEN2`
implementation was found in the inspected Mail executable, Mail, MailCore,
MailService, MailSupport, libsasl2, or token plugin. This does not establish
whether Sierra can obtain a different credential accepted by the older protocol;
it does not supply a reference for implementing `ATOKEN2` on Mavericks.
Neither image was mounted or installed, and no account authentication was tried.
All temporary installer archives, extracted binaries, disassembly, and archive
reader files were removed after inspection; the original downloads were retained.

### Mail credential trace on Mavericks

Local disassembly and a bounded trace of the running Mail process on 2026-09-09
established the following path:

1. The adapter exchanges the GrandSlam password-equivalent token at
   `/setup/authenticate/<account>` and obtains `tokens.mmeAuthToken`.
2. The subsequent account-settings response passes back to the native helper.
   Earlier service diagnostics established that its returned MME token was
   present and unchanged from the token used for that settings request.
3. AOSKit's `AOSKPersistMailProperties:` copies `tokens.mmeAuthToken` into
   `kAOSMailAuthTokenKey` (`mailAuthToken`), alongside the account's person ID.
4. `MFAosImapAccount appleAuthenticationToken` retrieves that mail property through
   `_AOSAccountRetrieveMailProperties`. The SMTP account delegates to the IMAP
   account for both its person ID and token.
5. MailCore's `_MCAppleTokenSaslClient` constructs the native ATOKEN response.

The configured Mail address alias exists and resolves to the signed-in account's
DSID. Mail is configured for ATOKEN with TLS on port 993. The live trace observed
successful credential-property transactions and non-null ATOKEN responses.
It subsequently observed IMAP's failed-authentication response handler, Mail error
1032, and unsuccessful `executeAuthenticate:` results. Thus the observed failure
occurs after local credential retrieval, at IMAP authentication. This does not
prove that ATOKEN2 is required or that a separately issued Mail token is needed.

One normal Get Mail check was requested for the sole iCloud account; the traces
also observed Mail's own retries. They recorded presence flags, outcome flags,
and numeric error codes only. They did not record account identities, credential
values, server response text, or messages. Both traces exited automatically.
No account was signed out and no system code was changed for this investigation.

A concrete untested difference remains in token issuance: `aq_apple_request`
supplies the adapter/provider client identity to the authenticate exchange.
The original native client identity is restored only on the later settings
request. Whether preserving the native identity during token issuance changes
the credential Apple issues remains unverified. The old working token was not
retained, so its format cannot be compared with the newly issued token.

The exchange uses SRP-6a with the RFC 5054 2048-bit group, SHA-256 and Apple's
`s2k`/`s2k_fo` password transformations. It validates integer bounds, rejects invalid
server public values, verifies the exact-length M2 proof with a constant-time
comparison, and only then decrypts the session data using AES-256-CBC. Group
integers in the session key and proof hashes retain the full 256-byte group width,
matching CoreCrypto's SRP6a_HASH variant. The OTP is included in the GrandSlam
client-data plist, not duplicated in that exchange's HTTP headers. Secret
exponents and C key buffers are cleared when released. Foundation strings/data used
during an attempt are transient, but their storage cannot be guaranteed erased.

The resulting password-equivalent token authenticates with iCloud; the legacy
login-or-create route then fetches account settings using the returned DSID and
`mmeAuthToken`. The delegate route substitutes the token into its original plist.
Response URLs map back to the original request and stale length/encoding/cookie
headers are removed. Requests run on a serial worker queue with cancellation,
30-second per-request limits and a 4 MB response cap. Certificate validation stays
with the configured AquaTransport/system trust path. The module adds no trust bypass.

GSA diagnostics record stage/error codes, the credential transport format, and
whether account case was normalized, without
account names, passwords, device identifiers or tokens. The `debug` flag additionally
writes these codes to AquaTransport's log. Do not enable unrelated OS/framework
credential tracing to diagnose sign-in: AOSKit has its own logging behavior.

## Validation

`tools/gsa-selftest.sh` uses a catch-all mock URL protocol: no Apple request, real
credentials, or network access is needed. Coverage includes independent Python SRP
server vectors for `s2k`, `s2k_fo`, leading-zero salts, short public keys and short
shared secrets; invalid public values and
iteration counts; short/incorrect/repeated proofs; full token conversion; malformed
responses; missing anisette; refused redirects; trusted-device retry; cancellation;
endpoint scoping; conflicting rewrite rules; and
the real AOSKit CFURLConnection path, including Basic authentication with a
mixed-case account and password. Saved-token refresh tests cover native AOSKit,
missing anisette, redirects and exclusion of older tokens. DAV tests cover the native
request path, device headers, unchanged methods and bodies, streamed response
chunks and DAV headers, authentication-challenge replies, cancellation, redirect
header removal, host scoping, native discovery usernames and legacy ports, provider failure and
the disable flag. Mail tests load Mavericks' actual MailCore with a synthetic
account and exercise the C TLS trigger, six-field response, challenge replies,
IMAP/SMTP host scoping, device cache, provider failure, legacy-token preservation,
and both initial and runtime disabling. MailCore is available only to x86_64
non-GC processes on this machine. The remaining suite runs both Intel architectures plus a
64-bit GC-enabled host. `tools/gsa-diagnose.m` tests the production provider path
without reading credentials or starting Apple sign-in. Its `--request-vector` mode
checks the GSAPort signature format without network access. Running it without that
option can contact the provider and sends the device identifier as described above.
Live provider availability and Apple sign-in remain separate validation requirements.
